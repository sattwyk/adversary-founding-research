# Product alternatives and competitive comparison

Assessment date: 3 November 2026. Engineering-cost bands below are planning judgments for two experienced founders, not measured vendor development costs. A useful workflow includes workloads, an oracle, faults, debugging evidence and ongoing regression maintenance; a runnable simulator alone does not complete it.

## A–F: choose the initial product

| Alternative | Customer value and actual-code reach | Feasibility and integration | Differentiation and trust | Development / maintenance | Commercial path and expansion |
|---|---|---|---|---|---|
| **A. General deterministic framework** | Broad potential, but only code within controlled effects participates | Technically feasible; high retrofit burden or very expensive system-level control | Mature frameworks and commercial DST already exist; determinism helps replay but does not supply correct models | Very high; likely multi-year broad-runtime burden, not a credible first six-week product | Weak initial case; an ecosystem project before a clear paid outcome |
| **B. Rust/Go SDK over existing simulators** | Helps teams already close to a supported runtime; production logic under adapters | Moderate initial build, high dependency/toolchain coverage work; separate language paths | SDK ergonomics are copyable; escape detection and oracle quality determine trust | Medium initial build; high compatibility maintenance | Plausible niche, but no evidence two-language SDK is independently valuable; use adapters later |
| **C. Native faults plus history checking** | Direct value on existing multi-service binaries; little application code change | High feasibility; customer still writes workload/model and exposes recovery state | Existing Jepsen/Faultbox/Porcupine do much of this; native schedules remain uncontrolled | Low-to-medium initial orchestration; medium workload/model support | Useful delivery mechanism, weak standalone differentiation; natural broader-system path |
| **D. Broad hybrid verification platform** | Could combine strong native relevance and deeper model exploration | Components feasible individually; initial integration, semantics and UX scope are large | Credibility requires preserving different guarantees; a common badge is dangerous | High build and high cross-backend maintenance | Sensible eventual architecture after demand, poor initial promise |
| **E. Specialized persistence/crash product** | Precise costly release question; unchanged native code can participate | Feasible within a qualified Linux profile; recovery oracle required; namespace/storage fidelity is the hard part | Accurate profiles and minimized domain-specific witnesses can matter; existing research and vendors are strong baselines | Medium build for one profile; high if arbitrary filesystem/hardware support is promised | Most promising technical scope; commercial demand for a separate product unproven |
| **F. Recovery-contract qualification and maintained regression kit** | A finite deliverable: customer promise → trustworthy campaign → actionable regression | Reuse native and storage backends; one scoped integration at a time; no common scheduler | Differentiation hypothesis is recurring saved integration/debugging effort, not execution invention | Low initial service/tool layer; medium productization; support must fall with reuse | **Recommended.** Paid qualification first, recurring maintained release campaigns only if customers renew; expand contracts/backends from observed needs |

F is the go-to-market form of E, using C as an initial execution path. The longer-term module boundaries resemble a modest D, but building D's breadth is not a prerequisite. No additive feature score is used: the tradeoffs are not equally weighted or known precisely enough to justify one.

Do not position against ordinary unit tests instead. |
| **Gosim + bbolt scenario** | Actual Go library under modeled runtime, OS, disks and network; deterministic crash/restart | Measured same contract outcome in five seeds; Go 1.23.2 succeeded, installed Go 1.26.4 failed on this checkout. [Design](https://github.com/jellevandenhooff/gosim/blob/ffd3a613542675755e4cbf8186b5edaf404ed95c/docs/design.md) | Sufficient for the demonstrated Go loss. | **Turmoil / MadSim** | Useful Rust simulation runtimes and compatible dependency interfaces | Turmoil's inspected workspace includes unstable filesystem durability/torn-write support; MadSim upstream inspected power-failure stub is incomplete. Forks and imported API boundaries matter. [Turmoil](https://github.com/tokio-rs/turmoil/tree/6a1f50223b5a1884bf8890053c85eec04a8af267), [MadSim](https://github.com/madsim-rs/madsim/blob/519950efb4711464f300ed7edf2967ed62d5f502/madsim/src/sim/fs.rs) | Reuse where a customer already fits; avoid dual-runtime retrofit as the product's first requirement. |

Synctest ordering was variable in our executed probe. [Loom](https://github.com/tokio-rs/loom), [Shuttle](https://github.com/awslabs/shuttle), [synctest](https://pkg.go.dev/testing/synctest) | Complementary tools; already good solutions for many targeted concurrency questions. |
| **CrashMonkey/ACE, Ferrite, ALICE/BOB, Pathfinder** | Existing approaches to crash modeling, recording/replay, bounded exploration and persistence dependencies | Scope, kernel/tooling compatibility, workload/oracle adaptation and ongoing packaging need investigation. [CrashMonkey](https://github.com/utsaslab/crashmonkey), [Pathfinder](https://dl.acm.org/doi/full/10.1145/3720431) | Prior art and candidate infrastructure. | **Maintained customer harness** | Exact domain knowledge, production build integration and established regression expectations | Expensive when only one engineer understands it; otherwise often the best answer | Adversary must beat ongoing maintenance/debugging effort, not the zero license price. |

## Defensibility assessment

| Hypothesis | Assessment | Falsifier |
|---|---|---|
| Easy integration of existing code | Necessary, weak moat by itself; competitors already do it | Existing-tool integration reaches the same check in equal or less customer time |
| Accurate storage profiles | Potential earned trust, but costly and narrow | Calibration reveals impossible witnesses or missed known failures; customers need too many profiles |
| Domain contracts/workloads | Best accumulation hypothesis when reusable across independent customers | Every integration needs a bespoke oracle with little reuse |
| Counterexample diagnosis and regression maintenance | Potential recurring value if it saves repeat labor | Customers use one audit and never rerun; native failures remain too flaky to diagnose |
| Exploration efficiency | Valuable only with measured improvement at equal fault/contract scope | Strong existing baseline finds the same defects within comparable budget |
| Cross-language orchestration | Practical compatibility feature, little standalone moat | Competitors meet the same workflow; likely already true for native systems |
| Autonomous agent interface | Useful distribution/interface choice, easy to copy | Structured outputs add no value beyond an ordinary executable regression |

The strongest hypothesis is a growing body of calibrated recovery profiles, reusable domain contracts and maintained minimal failures that materially lowers the next integration's cost. There is no network effect or data moat demonstrated. Customer code and failures may be private; cross-customer learning requires consent and abstraction, not assuming ownership of their artifacts.

Test defensibility through paired customer tasks: Adversary versus the customer's best existing option, with equivalent assistance and identical guarantees. Measure customer effort to first useful result, time to explain a failure, and maintenance after a real code change. Win on those outcomes or narrow/pivot. A cheaper clone of a broad simulator is an unattractive initial strategy.
