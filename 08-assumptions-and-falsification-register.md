# Assumption and falsification register

Confidence is a qualitative judgment requested for this investigation, not a probability estimate. “Strong” is restricted to the tested boundary or directly inspected code. Proposed thresholds are investment decisions, not research findings. No commercial assumption is considered validated.

| ID | Assumption and decision contingent on it | Supporting evidence | Confidence | Falsification test and action |
|---|---|---|---|---|
| A1 | Customers need help maintaining recovery promises, beyond buying execution capacity | etcd/RisingWave custom harnesses; commercial testing accounts | Tentative commercially | Ten qualified conversations and paired integration tasks; if existing tools solve the job adequately, abandon standalone platform thesis |
| A2 | A useful native integration can avoid upstream source edits | redb and bbolt wrappers, zero library edits | Strong for small selected libraries; unknown for services | Three independent application integrations; if most need more than one customer day or invasive changes, narrow to a specific existing boundary |
| A3 | A shared contract/evidence envelope is valuable across languages | Same predicate and four exported native artifacts | Strong at pair-recovery boundary | Implement a Rust/Go multi-service scenario and a second contract; if adapters leak semantics into common fields, keep only a minimal result envelope |
| A4 | One shared deterministic scheduler is unnecessary initially | Native recovery probes and existing-tool baseline worked | Strong for selected workflow | Customer-critical bug cannot be exposed or diagnosed without schedule control; use a maintained backend before building one |
| A5 | Process-crash testing alone is insufficient for durability qualification | bbolt relaxed mode survived native kills and lost data under reconstruction/Gosim | Strong for tested versions/scenario | Calibrate a real-filesystem power-loss case; do not generalize the measured loss frequency to all systems |
| A6 | A trustworthy storage runner can be built by composing existing infrastructure | Kernel block replay tools and crash-testing prior art | Plausible, unmeasured | Qualify directory, rename, truncate, barrier and recovery cases; if acknowledgment correlation or semantics remain unsound, sell only narrower supported evidence or stop persistence product |

| A13 | Qualified customers will pay for a maintained workflow | Public category pricing/adoption only | Unproven | Obtain two paid pilots with a budget owner and reason beyond discounted consulting; failure triggers stop/pivot gate |

| A17 | Rust/Go is a useful initial customer filter | Native examples selected for technical relevance | Tentative | Interview prospects by durability problem rather than language. Accept other native languages through the same interface if they provide better paid learning. |
| A18 | A local/ BYOC path improves adoption | Sensitive source/snapshots are a foreseeable constraint; no measured customer preference | Tentative | Ask qualified buyers to choose deployment and perform installation; do not build enterprise controls without a funded requirement |
| A19 | A finite recovery deadline is a useful property | Common practical need; no chosen customer's latency contract | Conditional | Customer specifies healed-fault period and acceptable bound. Otherwise report timeout as inconclusive, not liveness violation. |
| A20 | Autonomous development agents increase long-term value | Mission-level hypothesis only | Speculative | Existing engineers must buy the initial product independently; if not, AI positioning does not rescue the near-term business |

Committed design constraints: honest evidence categories; explicit failure semantics; actual implementation recovery; bounded integration scope; a usable local artifact; no green result from missing evidence. Revisit language focus, licensing details, deployment, backend selection and pricing as experiments warrant.

The most consequential unresolved pair is A6/A13: technically faithful storage evidence and actual willingness to pay for maintained contracts. Success on only one does not justify building a verification company. At six weeks, use the gates in the decision memo to continue, narrow to an integration service, partner with an existing execution vendor, or stop.
